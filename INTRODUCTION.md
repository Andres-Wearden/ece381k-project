# Introduction

Multi-agent artificial intelligence systems are now common in many areas of technology. They coordinate autonomous vehicles on roads, support federated learning across phones and sensors, moderate content across large platforms, and run on edge devices with limited resources. In all of these settings designers make a choice about who communicates with whom, yet this communication pattern is often treated as a minor implementation detail. Our work shows that this choice matters. The layout of the network that connects agents can change final accuracy by several percentage points and can strongly influence how robust the system is to noise and failure. This observation leads to the central question of this report: **How does network topology shape collective intelligence in multi-agent systems?**

## What is Interesting About This Project?

This project is interesting because it reveals that network topology—the pattern of who talks to whom—is not just infrastructure but a fundamental design parameter that directly shapes learning outcomes. Most research in multi-agent systems focuses on improving individual agent algorithms or optimizing communication protocols, but treats the underlying network structure as a given. We show that the same learning algorithm, running on the same data, can produce meaningfully different results simply by changing how agents are connected. A star topology might converge faster but be fragile to hub failures, while a mesh topology might be more robust but require more communication overhead. These tradeoffs are not obvious a priori, and our systematic benchmarking framework makes them visible and quantifiable.

What makes this particularly interesting is that we can observe these effects even when agents use simple, well-understood models like logistic regression. This suggests that topology effects are fundamental to distributed learning, not artifacts of complex algorithms. Moreover, we find that different topologies suit different model types differently—what works well for neural networks may not work as well for graph attention networks, creating a rich design space where topology and model choice interact in non-trivial ways.

## Big Idea

The central idea of this project is that network topology is not merely plumbing for messages. It is a primary design choice that shapes how multi-agent systems learn, share information, and perform on real tasks. The pattern of connections among agents—whether arranged as a star, ring, mesh, tree, cascade, or more complex structures like small-world or scale-free networks—determines how quickly information moves through the system, how errors spread or are corrected, how much communication is required, and how well the system tolerates failures. When an agent updates its model using messages from specific neighbors rather than from the entire population, the structure of those neighbor relationships becomes part of the learning process itself.

Our results show that even modest changes in topology can lead to meaningful differences in performance. Changing only the communication pattern and holding the learning algorithm and data fixed can create accuracy gaps of several percentage points. The same model can reach different accuracy levels under different topologies, with variations that depend on the specific topology-model combination. To study these effects in a controlled way we built a benchmarking framework that evaluates a range of topologies across multiple agent models and datasets. The framework currently supports **nine network structures** (star, cascade, feedback-rewired, ring, mesh, small-world, scale-free, tree, and grid) and **four types of agents** including logistic regression, feedforward neural networks, graph attention networks (GAT), and random forests. Together these experiments provide a systematic view of how network structure shapes learning dynamics in multi-agent systems, revealing both expected patterns (like the robustness of mesh topologies) and surprising findings (like how certain topologies can amplify or dampen the strengths and weaknesses of different model architectures).
